## 3. 진단 — 이건 개별 오류가 아니라 **문서 성장 방식의 결함**

**Append-only 성장:** 새 발견을 부록에 덧붙이지만, 앞장의 원 주장은 손대지 않는다.
문서가 커질수록 자기모순이 **누적**되고, 정정이 부록에 격리될수록 본문의 오래된 서사가 오래 산다.

이것이 ChatGPT가 "방법론" 문제로 지적한 것의 실체일 가능성이 높다.
개별 숫자를 아무리 고쳐도, **성장 방식을 안 고치면 다음 세션에 같은 부결이 재발한다.**

정정 선언의 문서 내 위치 분포가 진단을 뒷받침한다:
- 강등 3건 → 80%, 80%, 94%
- 재현 실패 1건 → 80%
- 원 주장 → 20~48%

## 4. 감사 도구 자체의 한계 (정직 보고)

`audit_whitepaper.py`는 **두 번 틀렸다.**

- **v1 (너무 느슨):** 마커 목록에 "정정"이라는 범용어를 넣어, 48% 지점의 *무관한* 용어 정정이
  20.1% 문제를 가려버림 → **20.1%를 0건으로 통과시킴(위음성)**. 사람 눈이 먼저 잡았다.
- **v2 (너무 조임):** 값 충돌 정규식을 조이자 PBO 57.5%/0.571 병존을 놓침 → **위음성**.

교훈: **정규식 감사는 튜닝 지점이 존재하며, 그 튜닝 자체가 과최적화 대상이다.**
PBO 문제의 문서판이다. 정규식을 무한히 조율하는 대신 **구조를 바꿔야 한다**(§5).

알려진 잔여 결함: 섹션 헤더 매핑이 깨져 모든 히트가 "1.3 토대 데이터"로 표시됨.
문서 위치(%)는 정확하므로 판정에는 영향 없음.

## 5. 구조적 처방 — 숫자 SSOT

정규식으로 사후 적발하는 대신, **애초에 모순이 불가능한 구조**로 간다.

### 5-1. 백서가 숫자를 하드코딩하지 않는다

```
기준값.json  ←  파이프라인이 생성 (유일한 진실)
    ├→ 백서 렌더링       {{ PBO }} → 57.5%
    ├→ 대시보드 렌더링    {{ PBO }} → 57.5%
    └→ 세션정리 렌더링    {{ PBO }} → 57.5%
```

한 곳만 바뀌면 세 문서가 동시에 바뀐다. 문서 간 불일치가 **원천적으로 불가능**해진다.

### 5-2. 클레임 레지스트리 (`클레임_레지스트리.csv`)

각 주장에 ID·상태·근거를 붙인다. 강등은 **문장을 지우는 게 아니라 상태를 바꾸는 것**이다.

| status | 렌더링 |
|---|---|
| `active` | 정상 표시 |
| `superseded` | 취소선 + "→ 대체: C-018" 배지 자동 삽입 |
| `retired` | 본문에서 제거, 부록 '폐기 이력'으로 자동 이동 |

C-003(20.1%)의 status를 `retired`로 바꾸면 **본문 20%·21%·47% 세 곳이 동시에** 처리된다.
지금처럼 사람이 세 곳을 기억해서 찾아 고칠 필요가 없어진다.

### 5-3. 빌드 게이트

백서 빌드 스크립트 마지막에 `audit_whitepaper.py`를 걸고, 무마킹 잔존이 1건이라도 있으면
**빌드 실패로 산출물을 만들지 않는다.** forward 사양서의 게이트와 같은 사상이다.
